# 正文与附件

[← 架构](../architecture.md)

正文在打开时下载（`MailClient::download_message`）；开着后台预取的前端（GUI、`catmail watch`）另在后台
把没下载的正文取下来，让没打开过的邮件也能按正文搜到（见[后台预取](#后台预取)）。所有按需操作经过同一个入口
（`catmail-core/src/body.rs` 的 `on_server`）：从连接池取连接、EXAMINE 比对 UIDVALIDITY（连接已经
只读打开着同一个文件夹、UIDVALIDITY 一致、邮件在打开之前就已到达时省掉，见[连接池](protocol.md#连接池)）、在账户的取消信号上
select。打开文件夹、取信、判断邮件是否已不在服务器上这一段（`in_folder`）与连接无关，后台预取在自己的连接上
用同一段。

## 两条下载路径

按 RFC822.SIZE 分（界限默认 2 MiB，即 `EngineTuning::whole_message_limit`，测试和按流量计费的
用户可以在 builder 上调）：

- **≤ 2 MiB：整封下载。** `UID FETCH <uid> (BODY.PEEK[])`，原文存入 BlobStore
  （`message_bodies.raw_blob_hash`），解析后附件随即解码入库。绝大多数邮件走这条路：完整原文
  最不依赖服务器 BODYSTRUCTURE 的正确性，也留下了 `.eml`（转发、查看原文、以后换解析器重建）。
- **> 2 MiB：按部分下载。** 先取 BODYSTRUCTURE，只取会作为正文显示的部分（单个不超过 2 MiB）；
  附件只记录 section、传输编码和估算大小，第一次打开时再 `BODY.PEEK[<section>]` 下载、解码、入库
  （`MailClient::attachment_content`）。超过 2 MiB 的正文部分和附件一起列出（`text/plain` 或
  `text/html`，没有文件名），打开时单独下载，内容不会无处可看。
- **退回整封下载**：BODYSTRUCTURE 解析失败，或服务器对要取的正文部分回 NIL、干脆不回。缺了正文
  的结果一旦按"已下载"存下，就再也不会重取。`raw_message` 遇到尚未下载的大邮件时整封下载一次，
  同时存下正文。

## 后台预取

`MailClientBuilder::prefetch_bodies(Some(BodyPrefetch))` 时，引擎为每个账户起一个任务
（`catmail-core/src/prefetch.rs`），与后台同步在同样的地方启动（引擎打开、添加账户、撤销删除）。括号里是
`BodyPrefetch` 的默认值。

- **自己一条连接**，不用连接池：池里每账户只有 2 条，打开邮件不能排在预取后面。Gmail 每账户最多 15 条并发
  连接，加上后台同步、完整同步、连接池仍远不到。没事做时（取完、预算用完、出错后等待）关掉连接，不占服务器的
  名额。不拿同步锁，不挡同步。
- **何时开始。** 账户的所有文件夹同步完一次之后（`Engine::synced`；睡醒之后、要求立即同步之后也等到再同步完
  一次），首次同步时不与拉邮件头抢带宽。完整同步结束没有事件可听（什么都没变时一个也不发），引擎另有每账户的
  `synced_signal`。取完之后等账户的消息（`MessagesChanged`、`AccountStatusChanged`，落后了也算）再看，同步
  拉来的新邮件随即取下；最多等一小时，失败过的邮件到期后也会再试。
- **取哪些。** 本地没下载、在服务器上有 UID 的（本地移动、还没回放的等回放之后），从新到旧
  （`Prefetch::next`）。已删除、垃圾邮件文件夹里的排在其他所有位置之后：最少有人找，但问服务器的搜索会问
  每个有正文缺失的文件夹，它们取完之后才不必问。查询走部分索引 `messages_prefetch`（只含没下载、有 UID 的行，
  随正文到来变小），不必每批把账户的邮件读一遍再排序（10 万封时约 17 ms → 0.1 ms）；先查其他位置、一封也没有
  了再查已删除和垃圾邮件，两次各自走这个索引。一批之内按文件夹排一下，普通账户上按日期交错的几个文件夹不会
  每封切换一次（每次多一个 EXAMINE）；所以两类不放进同一批，否则 id 小的已删除会排到前面、先用掉当天的额度。Gmail 上一个 `X-GM-MSGID` 一行，不会因为标签重复下载；普通账户上同一封
  邮件在两个文件夹是两行，各取一次。
- **取多少。** ≤ 256 KiB（`whole_limit`）的整封下载，与打开时相同：离线也能看附件、留下原文。更大的只取
  正文部分，附件等打开时再取；单个正文部分的上限仍是 `whole_message_limit`，否则大的 HTML 会被列成附件、打开
  时也不再取。和打开邮件写入同一张表、走同一个 `store_body`，打开的人与预取的人同时取到时只写一份。
- **每日预算。** 每个账户每个 UTC 日取到的字节数记在 `prefetch_usage`，与正文在同一个事务里累加，重启后接着
  算。算的是取回的字节（整封的原文，或正文部分加上重读的 MIME 头），打开邮件不算。超过服务器的下载限额，账户的
  IMAP 会被锁一段时间，期间同步、打开邮件全都不能用，所以预算按服务器分（看账户的 `gmail_server`）：
  - Gmail（`gmail_daily_budget`，1 GiB）：官方限额是每天经 IMAP 下载 2500 MB（Workspace 的
    [Gmail 带宽限制](https://knowledge.workspace.google.com/admin/gmail/gmail-bandwidth-limits)；个人账户没有
    官方说明，用户报告的数字相同），超过后暂停"通常 1 小时，最长 24 小时"。官方没说是滚动的一天还是自然日；跨
    UTC 零点两边各取满也只有 2 GB，余下的留给打开邮件和同一账户上的其他客户端（官方特别提醒，多个客户端各下载
    一遍）。
  - 其他服务器（`daily_budget`，200 MiB）：多数不公布限额。网易（163 / 126 / yeah）确认有 IMAP 每日流量上限、
    不公布数值，超过后客户端最长 24 小时不能收发，开会员也不提高第三方客户端的上限；有用户同步两千多封就碰上
    （2026-11-01 查证时的资料）。QQ、iCloud、Outlook.com 没找到公开的下载限额。200 MiB 只取正文约几千封，是为
    保险定的数，不是依据。
- **服务器说超限了**（`imap::Error::is_over_limit`，proto 里按文字认）：预算之外的兜底，限额未知或其他客户端
  用掉了额度时，撞上一次就停。按回复的
  文字认，不论出现在登录、打开文件夹还是 FETCH 上：Gmail 的 `[ALERT] Account exceeded command or bandwidth
  limits`，网易的 `Fetch volume limit exceed` 和 "flow over limit"。认出后不给邮件记失败，把暂停到的时刻（24
  小时后，两家说的最长锁定时间）写进 `prefetch_usage.paused_until`，重启后也照样等。只停预取，不改账户状态：
  同步、打开邮件照常去试，它们也认得这种回复（`Error::OverLimit`），同步按 `over_limit` 放慢重试、账户状态显示
  超限，打开邮件报出能看懂的错误（见[同步 / 后台同步](sync.md#后台同步与-idle)）。反过来，同步报告了超限时
  预取不开始（`may_start`），等同步再次成功（那是一条账户消息）再继续，不另停 24 小时。
- **一批一个事务。** 每取 20 封（`batch`）写一次：正文、失败记录、用量在同一个事务里，提交后每个列着这些邮件的
  文件夹（Gmail 上包括标签和 Starred，见[正确性](#正确性)）发一次 `MessagesChanged`（摘要和附件标记变了）。一批中途出错，已取到的照样写下，不白下载。任务每批之间放开
  引擎的强引用，关掉客户端时最多等完手上这一批。
- **失败分两种。**
  - 这封邮件的：服务器拒绝（NO、答复解析不完整），或说有这封邮件却不给内容（协议错误，丢掉连接）。记进
    `prefetch_failures`，一小时后再试，之后每次是上次的四倍，最长一周；正文写入时（不论谁取的）删掉记录。
    这样一封总是取不下来的邮件不会让后面的都卡住。连着三封都这样时（跨批也算，计数在任务里，不在一批里：批小到
    1、2 封时也停得下来），多半是服务器在拒绝的不止这几封（如没认出来的超限回复），整个任务停一小时，不再给后面
    的邮件记失败。
  - 账户的：断线、超时、新连接登不上。不记在邮件上，按 `retry`（30 秒）加倍等待，最长 30 分钟。登录被拒不再
    自己试：每次都是又一次失败的登录，服务器会算进锁账户；等后台同步（或用户）的一次完整同步在被拒之后成功了
    再继续。这次同步先发"同步完成"的信号（`set_synced`），之后（LOGOUT、后台同步还要同步 INBOX）才在
    `report` 里清掉"登录被拒"、发 `AccountStatusChanged`，所以等同步时也听账户的消息，否则会错过恢复、一直等到
    下一次完整同步。账户状态归同步管，预取的失败只记日志。
- **文件夹在服务器上重建了**（UIDVALIDITY 变了，`body::folder_rebuilt`）：它的邮件在下次同步重来之前一封也取
  不了，逐封试只会每封多一次 EXAMINE。记进内存里的跳过名单，下一次等待结束（多半是同步之后）清空。邮件已不在
  服务器上（`OutOfSync`）、本地行已没了的直接略过。
- 读仍然只用 EXAMINE 和 `BODY.PEEK`，不会标为已读；不渲染 HTML，不加载远程图片，发件人得不到任何信号。
- **日志**（`catmail_core::prefetch`）：状态的变化在 info / warn，默认就进日志文件：任务启动时的参数、每批的封数
  / 失败数 / 字节数和当天已用 / 预算、预算用完、超限（服务器原话、那封邮件、当天已用、是否 Gmail）、重启后仍在
  暂停（到何时）、连续被拒而暂停、逐封的失败、账户级的失败（错误类型、退避）、全部取完。逐封的细节（大小、实际
  下载的字节、整封还是只取正文、EXAMINE 和 FETCH 各用多久）在 debug，要时用
  `CATMAIL_LOG=catmail_core::prefetch=debug` 打开。
- **代价：正文存得更早。** 预取让大多数正文在打开之前很久就存下，之后改了解析或清洗规则，靠[重建](#按版本重建)
  跟上；只取了正文部分的大邮件没有原文，放开的规则对它们不生效。

## 同一套提取逻辑

按部分下载时，用 BODYSTRUCTURE 和取回的部分**重建一封结构相同的替身邮件**（没取的部分是空的
base64 正文），交给 mail-parser 按同样方式解析。于是两条路径选出的正文部分、字符集与传输编码的
解码、RFC 2047 / 2231 文件名完全一致；"哪些部分会显示"也是在不含数据的替身邮件上用同一套规则
判定的。

- BODYSTRUCTURE 的值来自服务器：写进替身邮件头之前去掉换行，token 只保留合法字符，不能伪造邮件头；
  叶子部分即使自称 `multipart` 也按 `application` 写出、去掉 `boundary`，否则它会吞掉后面的部分、
  打乱 section 编号。
- 替身邮件解析出的部分对不上 BODYSTRUCTURE 的 section 时一律视为未下载。
- IMAP section 编号按 RFC 3501 §6.4.5 从解析结果计算，附加的邮件（message/rfc822）算一个部分。

## 原始字节的邮件头

有的邮件程序把附件文件名、主题、显示名直接用发件人本地的字符集（如 GBK）写进邮件头，不按 RFC 2047 / 2231
编码。mail-parser 和 imap-proto（BODYSTRUCTURE）都按 UTF-8 有损读，不是 UTF-8 的字节变成 `U+FFFD`。

- 转码在 `mime::transcode_fields`：一个字段一个字段地看，合法 UTF-8 的字段原样保留（其中的 `U+FFFD` 是发件人
  自己写的），其余的用线索里第一个能完整解码（encoding_rs 不做替换地解码成功）的字符集转成 UTF-8，再整体重新
  解析。先转码再解析：GBK 等双字节的第二个字节可能是 `\` 或 `"`。
- 线索是同一封邮件里文本的 `charset`（其他客户端也这样猜），按 MIME 顺序取所有文本部分（`text/*`）的；整封邮件、替身邮件和 BODYSTRUCTURE（同步时的摘要邮件头，见
  [同步](sync.md#邮件头)）用同一条规则。附件文件名先试这个部分自己的 `charset`。没有线索就保持原样，不做
  字符集探测。
- 只用 encoding_rs 认识、ASCII 兼容的编码（`legacy_encodings`）：UTF-16、ISO-2022-JP 会把字段名、冒号和换行
  也当成文字解码，解得通却毁了邮件头的结构。UTF-8 不算（这些字段不是）；ASCII 也不算，它说明不了发件人用
  什么字符集，而且按 WHATWG 它的标签（`us-ascii`、`ascii`、`ansi_x3.4-1968`）指 windows-1252，什么字节都
  解得通。其他 ASCII 别名 encoding_rs 不认识，自然不用。
- 附件文件名只在含 `U+FFFD` 时重读。整封下载时原始头就在原文里；按部分下载时，BODYSTRUCTURE 里参数值带
  `U+FFFD` 的部分（`MimeNode::garbled_sections`）另发一条 `BODY.PEEK[<section>.MIME]`，取回的头交给同一套
  逻辑。这条 FETCH 解析不了就只是文件名保持原样；只有这种邮件多一次往返，不并进取正文的那条（那条缺项会
  退回整封下载）。

## 正文的组成

- `text`：所有正文文本部分；只有 HTML 时由 HTML 转换。
  - HTML 转文本用的是**清洗后**的 HTML（mail-parser 的 `html_to_text`）。直接转发来的原文不行：
    mail-parser 只认不带属性的 `<style>`，`<style type="text/css">` 里的规则会成为正文、摘要和索引的开头；
    它跳过 `<head>` 的办法也和浏览器不同。清洗后只剩开头一个不带属性的 `<style>`，`<title>` 连同文字被
    去掉，转出的就是读信区显示的文字。只有 HTML 的邮件（最常见）直接转已经清洗好的 `html`，不另清洗一遍。
  - 发件人的 `text/plain` 按原样取，除非它其实是标记（`is_markup`）：有的发件人把 HTML 源码或样式表放进
    文本部分（整份，或者开头一大段样式表、后面才是正文）。判断看文本开头 1000 个非空白字符：落在标签
    （`<p>`、`</td>`、`<!…>`，不含 `<https://…>` 这样的链接）、`/* … */` 注释或花括号块里，**并且**不出现在
    HTML 转出的文字里的词，占一半以上，就改用 HTML 转出的文本；HTML 转不出文字时（比如只有图片）保留原文本，
    带着标记也比什么都没有好。看开头，因为列表、读信区和 agent 先看到的是开头；要求 HTML 里看不到，是为了不误伤讲代码、讲 CSS 的邮件（GitHub 通知、代码求助），它们的 HTML 也
    显示同样的代码。误判的代价也小：HTML 是同一封信的另一种形式，换过去最多丢掉文本的排版。放弃的方案：
    有 HTML 就一律从 HTML 转（发件人写的纯文本通常更好，读信区和 MCP 都优先用它）；只按标记所占比例判断
    （代码多的纯文本会被误判）。扫描是线性的，长度由发件人决定。
- `html`：只在有真正的 HTML 部分时存在。proto 解析正文时用 `catmail-html` 的 `sanitize_html` 清洗
  （经 `ammonia`）。这个 crate 只管 HTML：清洗，以及读信区在清洗结果上做的几遍处理；纯函数，不碰
  协议，前端经 `catmail_core::html` 使用。清洗规则：
  - 去掉脚本、表单、iframe、事件属性和 `javascript:` 链接；`<title>` 连同文字去掉（ammonia 去掉不允许的
    标签时保留里面的文字，标题会显示成正文的第一行）；
  - 样式表不交给 ammonia（它不看 `<style>` 里面，写回时原样输出原始文本）：分词时按树构建器的规则
    （`script`、`textarea` 等之后切到原始文本，SVG / MathML 里的忽略）取出 `<style>` 的内容，经
    `css.rs` 用 cssparser 的记号逐条重写，合成一个 `<style>` 放在输出开头。每张表单独解析（没写完
    的规则随它的表结束，不吞掉下一张）；带 `media` 属性的表包进 `@media <属性值>{…}`，属性值按
    `@media` 的条件重写，不是媒体查询列表就整张不用（浏览器也当它 `not all`）；`type` 不是空或
    `text/css` 的（模板等）浏览器不应用，这里也跳过。记号写回时按 cssparser 的
    `needs_separator_when_before` 在必要处插入 `/**/`：注释在分词时就没了，`u/**/rl(` 直接拼起来会
    变成没检查过的 `url(`，`1px/**/2px` 会变成一个尺寸。只保留普通规则和
    `@media` / `@supports`（最多嵌套三层）；值里有 `url()`、`image()`、`image-set()`、`cross-fade()`、
    `src()`、`element()`、`paint()` 的声明丢掉，规则其余部分保留（转义在分词时已解码，`\75rl(` 就是
    `url(`）；`@import`、`@font-face` 等其他 at-rule、带 `:has()` 的选择器、嵌套规则都丢掉；最多 64 KB、
    2000 条规则。输出里没有 `<`（写成 `\3c `），所以样式表不可能结束自己的元素或改变文档结构，变异
    XSS 不依赖 ammonia 对边角情况的处理。重写是幂等的，读信区对清洗后的 HTML 再清洗不会改变它；规则
    改了以后，已入库的正文按[版本重建](#按版本重建)。读信区的几遍处理（`serve_images`、
    `embed_inline_images`）只接受清洗的原样输出，样式表直接取开头那个 `<style>` 到第一个 `</style>`，不再
    把整封信分词一遍（大的营销邮件省下深色显示约四分之一的时间）；输出里没有 `<`，其它 `<style>` 都被
    ammonia 去掉，所以两种取法结果一样，有测试钉住。不是这种输入时只会丢样式表，不影响安全。
  - 读信区在深色主题下给 `serve_images` 传调色板，改写图片的同一遍里把颜色搬到深色页面上（`dark.rs`，
    见 [GUI](gui.md#深色)），返回值的 `dark` 说页面是否该用深色。先只按调色板重写样式表（便宜），有自己的
    深色样式（`prefers-color-scheme: dark`，或 `color-scheme` 含 `dark`）的不改色，页面仍是深色；样式表里
    用了 `var()` 的不改色，按浅色显示；其余的做一遍同时改图片和颜色的清洗，属性里的 `var()` 要到这一遍才
    发现，这时再做一遍只改图片的（这类邮件很少）。浅色、深色都是一遍，不再先改色再改图片地清洗两遍。转换在 OKLab
    里反转亮度（换算用 `color` crate），白色到读信区背景色、黑色到文字色，色相和饱和度保留（超出 sRGB 时降饱和度）。颜色按
    用途区别对待：背景（`background*`、`bgcolor`、阴影）只变暗，文字（`color`、`<font color>` 等）只变亮，
    这样文字和它的背景总是拉开对比，本来就深色的页眉和白字保持原样；边框直接反转，与周围的对比不变。
    文字在更短的范围里反转（`TEXT_RANGE`），否则白底上可读的灰字到深色上会发暗。颜色按 CSS 读（十六进制、
    颜色名和各种颜色函数，按解码转义后的记号交给 `color` crate），只在会取颜色的属性里认
    （`font-family: Tomato` 不是颜色），读不出的和全透明的原样保留，搬过的写成 `#rrggbb` /
    `#rrggbbaa`。颜色用了自定义属性（带颜色的属性值里有 `var()`）的正文不转换，
    按原样以浅色显示：变量在使用处取什么值由层叠决定，只有引擎知道，在定义处怎么
    改都保证不了每一对颜色可读（试过按用法定用途，多用途、变量互相引用、同名变量在不同规则里都会出错）；
    主流邮件客户端不支持 `var()`，邮件里很少用；
  - 保留表格布局属性和行内 `style`。`style` 属性和样式表走同一套重写：按一条规则的声明逐记号重写
    后写回（ammonia 按属性值转义），会取资源的声明（同上，外加 IE 的 `expression()`）和解析不了的声明
    只丢那一条，什么都不剩就去掉整个属性。浏览器读到的是重写的输出而不是原文，所以原文经浏览器错误
    恢复会留下什么不必另外判断；`!important`、厂商前缀、`mso-*` 等照常保留。空值的自定义属性
    （`--gap: ;`）也保留，写成一个空格：它和没设不同，`var(--gap, 1000px)` 不会用上后备值。浅色和深色用同一种
    `style` 规则，深色只是同一遍里多换颜色。`background` 属性（`<td background="…">` 的背景图）不在保留
    之列：要支持它，背景图得像 `<img>` 一样算进远程图片、内嵌部分和页面的图片消息，没有实际需求之前不做；
  - 链接只允许 http、https、mailto、cid，`data:` 只允许出现在 `img src`；判断时像 URL 解析器
    一样忽略其中的制表符、换行和开头的控制字符。
  - 图片地址（远程、`cid:`）原样保留，是否加载由渲染端决定，默认应拦截远程图片。
- **哪些是远程图片**由 `catmail-html` 决定（`serve_images` 改写页面时一并列出，经 `catmail_core::html` 导出）：
  清洗用的同一个 ammonia 配置遍历 `img src`，只留 `http` / `https`，按 `url` 解析后的写法（`remote_image_url`）
  去重，最多 200 张；列出的和页面里改写的是同一批。下载、缓存和读信区都用这一种写法，调用方传别的写法，缓存
  也会先规范化。
- **远程图片**只在前端要求时下载（GUI 是用户点"Show remote images"），`MailClient::fetch_remote_images`
  在引擎运行时上用 `catmail-proto` 的 `http::ImageFetcher`（reqwest，TLS 与邮件服务器共用同一个
  rustls + ring 配置）：
  - 只取 `http` / `https`，重定向最多 5 次且只能到这两种 scheme；只发 GET，不存 cookie，不发 `Referer`
    （重定向时也不发），User-Agent 是 `catmail/<版本>`。
  - 每张 30 秒、10 MiB 为限（先看 `Content-Length`，再边读边数）；一次最多 200 张，同时 6 个。
  - 类型先按开头字节认常见栅格格式（`catmail_html::sniff_image`，内嵌图片也用它；服务器常标成
    `application/octet-stream` 或标错），认不出再用 `Content-Type` 的 `image/*`，都不是就算失败。SVG 也算
    失败，不必缓存：它能带脚本和外部引用，邮件里的远程图片用栅格格式就够（起初是因为 GPUI 版的 SVG 解码器会
    按路径读本地文件）。
  - 返回一个流（`RemoteImageStream`）：每个 URL 下载完（或失败）就给出它的结果，按完成顺序，一张
    失败不影响其他；`next_ready` 不等待地取已完成的，前端可以把同时到的几张合成一批。流是 tokio 的
    channel，任何执行器都能等。丢掉流，引擎里还在下载的立即中止（`JoinSet` 随任务丢弃）。
  - 下载成功的图片进缓存（`image_cache.rs`，下面）；缓存里有的直接从缓存给出，不发请求。
  - 不拦截局域网和本机地址：与浏览器打开网页相同，且只在用户点击后、只对这封信的图片 GET。
- **远程图片缓存**在数据目录的 `remote-images/`，一个 URL 一个文件（文件名是 URL 的 SHA-256，内容是
  MIME 类型、换行、图片字节），第一次存入时建目录（0700，文件 0600）。
  - 不放进 `BlobStore`：blob 按内容寻址，可能与同内容的附件共用一个文件，只能在 GC 宽限期过后删；
    清除缓存要求立刻删掉。缓存文件没有别的引用，任何时候删掉都安全（缺了就是没命中）；写入经临时
    文件（`.tmp` 开头，读时忽略）改名，读到格式不对的文件就删掉当作没命中。
  - 缓存的图片可以不经用户同意直接显示（`MailClient::cached_remote_images`）：不发请求，发件人得不到
    任何信号。缓存按 URL，不按邮件：另一封信引用同一个 URL 也直接显示。不看 `Cache-Control`：
    邮件里的图片基本不变，按 `no-store` 再去取反而又给发件人一次信号。
  - 总大小上限 256 MiB，有新图片存入的那次下载结束后按最后使用时间（读取时更新 mtime）从最旧的删起。`image_cache_size`、`clear_image_cache` 给设置界面用。
- **内嵌**（`inline`）指正文把它当图片显示（proto 的 `mime::is_inline`）：HTML 里有 `<img src="cid:…">` 引用它
  （`catmail_html::cid_image_ids`，按 RFC 2392 取出完整的引用值、百分号解码后精确比较，`cid:logo-long` 不会让
  `logo` 也算内嵌），而且它能当图片显示（`image/*`，或发信端常标的 `application/octet-stream`，显示时按开头字节
  认类型）。其余部分都算附件，不管放在哪、别处怎么引用它：`cid:` 链接指向的、正文文字里恰好写着 `cid:…` 的、
  `<img>` 引用了却不是图片的（比如视频），都列在附件里，这样每个部分都拿得到。读信区和附件列表都只看这一个值
  （`MessageBody::inline_parts` / `files`），`has_attachments` 只统计非内嵌的部分。

## 按版本重建

每份正文记着做出它的内容版本（`message_bodies.content_version`，即 proto 的 `mime::CONTENT_VERSION`），
低于当前版本的重新做一遍（`catmail-core/src/rebuild.rs`）。版本管的是存下的整个 `Content`：解析（mail-parser、
字符集转码、只有 HTML 时转出的文本、哪些部分内嵌）和 `catmail-html` 的清洗，都会改变它。

- **何时换版本。** proto 的指纹测试（`fingerprint_follows_content_version`）钉住一组邮件解析、清洗后的结果，
  输出一变就失败，改的人当场决定要不要升版本：清洗收紧一律升；输出一样的重构不会碰到它。比较用 `<`：在新旧
  两个构建之间来回切换不会反复重建。
- **有原文的**（整封下载的，或后来为 `raw_message` 取过原文的）：从原文重新解析，正文、摘要、附件、
  `has_attachments` 和全文索引在一个事务里换掉（`Messages::rebuild_body`）。附件按 section 对上原来的行，
  保留 id（读信区手里拿着它）；新结果没有内容、原来已下载的，保留原来的内容。多数版本变化只改清洗，文本不变时
  不重写索引；附件内容已在 BlobStore 里的只算 hash，不再写一遍（`BlobStore::put_bytes`）。原文的 blob 在磁盘上
  找不到时按没有原文处理。
- **没有原文的**（按部分下载的大邮件）：清洗是幂等的，把存下的 HTML 再清洗一遍，收紧的规则就生效；内嵌按新
  HTML 的图片引用和部分的类型重新判定。清洗、取图片引用和判定内嵌，用的都是解析时的那几个函数（proto 的
  `mime::sanitized_html`、`mime::is_inline`；`Messages::refresh_html`）。文本保持不变，索引也不变：
  存下的不知道是发件人的文本部分还是从 HTML 转出的，版本 3 之前转出的可能带着样式表（#280），这类正文留着。
  放开的规则（以前去掉、现在允许的）对它们不生效：重新下载要占预取的每日预算、要连服务器，而且都是最大的
  邮件，所以接受。
- **打开时。** `download_message` 看到正文旧了，先重建再返回，用户看到的总是当前规则的结果；重建失败只记
  日志，照旧显示存下的正文。`get_message` 不重建。
- **后台。** 引擎打开后（`EngineTuning::rebuild_delay`，2 分钟）把旧正文全部重建一遍，让搜索也跟上。不由
  前端选择：没有旧正文时立即结束，短命的命令行在那之前就已关掉，留给下一次。只用本地的 CPU 和磁盘，不连服务器，
  所以不跟预取放在一起（预取按账户、要等同步、受预算限制）。一次就够：之后存下的都是当前版本。开始时列出要重建
  的 id（`message_bodies_version` 索引，没有旧正文时不必把正文表读一遍），每 20 封一个事务，解析在事务之外；
  批与批之间放开引擎的强引用。一封失败只记日志、跳过，下次打开引擎再试。提交后每个列着这些邮件的文件夹发一次
  `MessagesChanged`（见[正确性](#正确性)）。

## 正确性

- 用 UID 之前先 EXAMINE 并比对 UIDVALIDITY；不一致或服务器已没有这封邮件时返回
  `Error::OutOfSync`，交给下一次同步处理。FETCH 什么也没回时先用 `UID SEARCH UID <uid>` 确认，确认了
  没有就像同步那样删掉本地这一行（`Messages::delete_gone`，行仍在服务器上那个文件夹、
  UIDVALIDITY 和 UID 才删：本地移动过来、还没移动的行不删；查位置之后移动才做成的也不删，它已经在
  目标文件夹里，UID 和 UIDVALIDITY 可能碰巧相同）并发 `MessagesChanged`：否则它要留在列表和
  搜索结果里，直到下次同步那个文件夹，每次打开都失败。
- FETCH 什么也没回、而文件夹是复用的（没有 EXAMINE）时，先重新 EXAMINE、再取一次，然后才去 SEARCH：
  这条连接看到的文件夹可能比邮件旧（像 Gmail 那样对还没报告给这条连接的新邮件什么也不回）。复用前的
  UIDNEXT 判断已经排除了已知的原因，这一步是兜底：万一判断不全，代价是一次 EXAMINE，而不是报错，更不会
  在过时的视图上 SEARCH 落空、把服务器上还在的邮件删掉。只重开一次。
- 服务器还有这封邮件、却没回所要的内容（整封或某个部分为 NIL）时，不说"已不在服务器上"，而是返回协议
  错误：这条连接连同它看到的文件夹一起丢掉，再试会用新连接。
- 写入时只检查邮件行是否还在：message id 不复用，UIDVALIDITY 变化会删除旧代际的行，所以行还在
  就说明它仍是下载开始时的那个（文件夹, UID）。
- 正文、附件行、摘要、`has_attachments` 和全文索引在同一个事务里写入（`Messages::store_body`）；
  并发下载同一封邮件时只有一个写入，另一个直接读结果。提交后给列着它的每个文件夹发 `MessagesChanged`：所在
  位置，Gmail 上还有它的标签和 Starred（`Messages::touched_labels`；一行邮件在那些列表里也显示摘要和附件
  标记），打开、预取、重建都一样。
- 连接层把整条响应读进内存（见 [IMAP / 连接层](protocol.md#连接层)），所以附件是取回后再写入 BlobStore，不是流式落盘。
