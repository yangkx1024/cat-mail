# 操作队列

[← 架构](../architecture.md)

用户操作（`MailClient::set_flags` / `move_messages` / `archive_messages` / `delete_messages` /
`label_messages`）在**同一个 `write`
事务**里修改本地数据（乐观更新）并为每封邮件插入一条 `pending_ops`，提交后发
`MessagesChanged`、`PendingOpsChanged`。不会出现"界面已改，服务器永远收不到"。本地效果与
队列簿记在 `catmail-store/src/ops.rs`，回放在 `catmail-core/src/ops.rs`。

## 本地效果

- **标记**：只记录真正改变的位（已读的再标已读不入队）。回放用 `+FLAGS.SILENT` /
  `-FLAGS.SILENT`，从不整体替换，不影响其他客户端同时改的 flags，被拒绝时也能精确撤销。用户
  只能改 `\Seen`、`\Flagged`、`\Answered`。
- **移动**：邮件行立刻移到目标文件夹，`uid` 置空（只有本地移动过来、服务器还没移动的邮件才
  没有 UID），正文、附件、全文索引随行保留，离线也能读。服务器上仍按 op 记录的 (文件夹, UID)
  找它，所以没下载的正文照样能下载（`Messages::location`）。同步只比较有 UID 的行。
- **删除**：不在 Trash 里的移到账户的 Trash；已在 Trash 里或指定永久删除时 `\Deleted` +
  `UID EXPUNGE`（没有 UIDPLUS 只能用普通 EXPUNGE，会一并清除别人标了 `\Deleted` 的邮件——这正是
  那个标记的含义）。没有 Trash 的账户只能显式永久删除，不会悄悄变成永久删除。
- **标签**（Gmail）：本地立即改 `message_labels`（Gmail 移进已删除、垃圾邮件时自己去掉的标签也是，
  见[位置与标签](labels.md#操作队列)），每封邮件、每个标签一条 op（`label`，
  `target_folder_id` 是标签，`label_add` 是加还是去），只记实际改变的，回放用 `UID STORE
  +X-GM-LABELS` / `-X-GM-LABELS`，在邮件所在的位置里执行，从不整体替换（在 Gmail 设置里隐藏的
  标签不受影响）。"已加星标"不是标签，是 `\Flagged`。
- 回复发出（服务器接受，或用户确认已送达）时给原信加 `\Answered`，同样走队列。

用户的动作变成哪些改动由引擎决定：`MovePlan`（types，前端用同一个函数判断按钮和可选的目标）。
普通账户上移动、归档就是移动；Gmail 上大多数邮箱是标签，"移动"是改标签，只有进出已删除、垃圾邮件才
移动位置，归档是去掉 `\Inbox`。所以移动要带上用户正在看的文件夹（`shown_in`，搜索结果为空）：从标签
移走就去掉这个标签。规则见[位置与标签 / 操作队列](labels.md#操作队列)。

## 回放

`pending_ops` 每条记录绑定 `folder_id` + `uidvalidity` + `uid`。回放（`ops::replay`）发生在三处，
都持有该账户的同步锁：同步对账完文件夹之后、同步任何文件夹之前；`MailClient::replay_pending`
（只回放、不同步，用连接池里的连接，复用的连接已断开时在新连接上整个重来）；以及开启了后台同步时，
改动入队即唤醒后台任务，在它自己的连接上回放（见[同步 / 后台同步](sync.md#后台同步与-idle)）。
CLI 不开后台同步，在 `mark` / `mv` / `archive` / `rm` / `label` 后当场回放。服务器打不开的文件夹跳过，留给同步处理。

`replay_pending` 的 `ReplayReport` 统计每次尝试做了的事，失败的尝试也算：拒绝在发生时就已提交并撤销，
重来或下次回放都不会再看到它。连不上或中途断线不让调用失败，而是 `error`，计数是断线前做了的。草稿
按 ID 记：第一次被拒绝、重来时存上的不算被拒绝。

- **核对 UIDVALIDITY。** 按文件夹分组，`SELECT` 后只执行 UIDVALIDITY 与 op 自己记下的一致的；
  不一致的标为 `conflict`（`PendingOps::end_generation`，移动留下的无 UID 行随之删除），同步这个文件夹
  发现新代际时也会这样做。按 op 自己的那一代核对，而不是本地文件夹记下的：Gmail 的草稿邮箱是标签，
  本地不同步、没有 UIDVALIDITY，草稿旧副本的删除记的是 APPENDUID 给的那一代。被重建的是**目标**
  文件夹时，移进去、还没有 UID 的行留着：它们的移动记的是源文件夹的位置，照常回放。
- **顺序。** 同一文件夹里先回放标记，再回放标签，最后回放移动和删除：对已在本地移走的邮件改标记、
  标签，要在它离开那个文件夹之前到达。例外是在一次移动**之后**做的标签改动：它等这次移动（`pending`
  不给出它），随邮件到新位置再回放。移出已删除、垃圾邮件到某个标签就是这样：先 MOVE 到"所有邮件"，
  再在那里加标签。移动被拒绝时，等它的标签改动一起失败、撤销。
  - 等哪条移动在入队时记下（`after_op`：邮件正在移动中时，标签改动记下那条移动），而不是回放时按
    "同一位置上更早的移动"推出来：`pending` 和移动被拒绝时都只看这一列，以后别的改动要等移动也照此
    记下。移动做成后被删掉，这一列随之为空；移动途中又永久删除，移动改写成删除时等它的标签改动随之
    删掉：它们是冲着新位置去的，邮件到不了那里了；放出来回放的话，Gmail 上在已删除里加 `\Inbox` 会把
    邮件移出已删除，之后的删除就删不到它（见[位置与标签](labels.md)）。
  - 标记只需保持同一封邮件的先后，标签只需保持同一封邮件同一个标签的先后，所以分轮回放（每封的
    第一条、再每封的第二条……），轮内按改动分组，交替"标已读、加星标"也只需每种改动一条命令。
  - 一封邮件最多只有一条待回放的移动或删除（再次移动、删除改写的是那一条），所以它们可以按目标
    分组，相邻的同类操作合并成一条命令。
- **移动的执行。** 有 MOVE 用 `UID MOVE`，否则 `UID COPY` + `\Deleted` + 删除（见下文）。服务器
  给出 COPYUID 时本地行得到新 UID、**`MessageId` 不变**；否则删掉这一行，由下次同步重新拉取。
- **跟着移动的 op 同一次回放做完。** 移动做成后，仍指着原位置的 op（移动途中又做的改动、等它的标签
  改动、COPY 了结后跟到副本的）改指新位置；回放对还有没看过的 op 的文件夹（按（文件夹, op）记）再走一遍。
- **同一个标签的改动只做最后一条。** 一个文件夹的一次回放里，同一封邮件同一个标签的几条改动（加、去、
  再加）之间没有移动（标签改动在移动之前，等移动的要等它做完），加或去一个标签的结果只取决于最后一条，
  所以只发最后一条，前面的随它了结（`ReplayOp::superseded`，成功、拒绝都一起）。移出已删除到 INBOX、
  回放之前又删除时，`+\Inbox` 与 Gmail 移进已删除时去掉的 `-\Inbox` 都等那次移动，移动在本地了结后
  只发 `-\Inbox`，不会在已删除里给邮件加 `\Inbox`。
- **断线**保持 `pending`、记下尝试次数，之后重来。标记、标签、删除和 MOVE 执行两次都无害（服务器跳过
  不存在的 UID）；MOVE 做了而答复丢了，重做时找不到邮件、没有 COPYUID，本地行删掉、同步再拉。

## 被拒绝时撤销

服务器拒绝（NO/BAD）时标为 `failed` 并撤销本地改动：

- **标记**：每条操作记的是它实际改变的位，所以把这封邮件待回放的操作连同被拒绝的那条从新到旧
  逆推，正好得到它们之前的 flags；再把仍待回放的重新作用上去，并按现在实际改变的位重新记录。
  只撤销被拒绝的那一条是错的：先标已读、再标未读，两条都被拒绝，结果会是已读。
- **标签**：同样逆推，只看这封邮件同一个标签的操作：每条都改变了它，所以它们之前与第一条相反；
  仍待回放的重新作用上去，现在什么也不改变的删掉。
- **移动**：邮件回到原处，等它的标签改动一起失败、撤销。
- **删除**：本地行已经没了，下次同步把它拉回来。

`failed` / `conflict` 的记录留给用户查看（`MailClient::list_pending`、`catmail ops`）并由用户清除；
`pending` 的不能清除，本地已经改了。

## 没有 MOVE 的服务器

COPY 重做会多出一份，所以 COPY 像发信的结束标记一样处理（`ops::copy_move`）：

- 每次 COPY **之前**，用 `write_durable` 记下检查点：目标文件夹、它的 UIDVALIDITY 和 UIDNEXT
  （`pending_ops.copy_*`，用 STATUS 取，不必离开选中的文件夹）。这次 COPY 造出的副本 UID 只可能
  不小于这个 UIDNEXT。
- COPY 的答复带 COPYUID 时，删除原邮件**之前**再用 `write_durable` 记下每个副本的 UID（`copy_uid`，
  UIDVALIDITY 与检查点相同才记）。
- 有检查点的 op 在这个文件夹里**先于一切**核对，不论之后被改成了什么（移到别处、移回原处、永久
  删除），否则丢了答复的副本会留在目标里。记下了副本 UID 的，副本就是它（还在的话）；否则在目标里
  UID ≥ 检查点的邮件中找与原邮件**原文逐字节相同**的（每个副本只认领一次；先比服务器报告的
  RFC822.SIZE，只下载大小相同的，再比字节。RFC822.SIZE 不一定等于发来的字节数，有的服务器算法不同，
  所以大小只和大小比）：
  - 找到了：删除原处的，op 跟到副本那里（移回原处变成从目标移回，删除变成删除副本），回放随即
    再处理那个文件夹。
  - 没找到：COPY 没做成（或副本已被别人删掉），清掉检查点，op 照现在的样子继续。
  - 原邮件已经不在：COPY 之后的删除做成了而答复丢了（或别人删了它）。这时只能靠记下的副本 UID：
    还在就同上，op 跟过去（op 没变时行直接得到新 UID）；不在了说明副本也没了。没有记下（服务器没有
    UIDPLUS）或目标被重建时，op 没变的话邮件就在目标里，交给目标的同步；op 已被改过（移回、移到别处、
    删除）就标为 `failed`，提示用户去目标文件夹看一眼，否则用户删掉的邮件会在目标里重新出现。
- 绝不按 Message-ID 判断：目标里可能早有、或恰好在 COPY 前到达一封 Message-ID（甚至大小）相同而内容
  不同的邮件，当成副本会删掉它、留下真正的副本；没有 Message-ID 的邮件也没法找。
- 无法判断时（目标在此期间被重建或删除），op 标为 `failed`，**原邮件留在原处**，不再自动重试：
  宁可让用户看到可能多出的一份，也不丢信、不在背后复制第二份。
- COPY 被拒绝时什么也没复制（RFC 3501），照常失败；复制成功但删除原邮件被拒绝时，op 失败，邮件
  两边都有。

## 波及其他文件夹

文件夹从服务器上消失时，它的 op 随之级联删除，在此之前先撤销本地效果：从它移出的邮件行一并删除，
移入它的邮件回到原处。这些以及新代际造成的冲突都会改动**别的**文件夹里的行，所以 repository 返回
受影响的文件夹（`Touched`），提交后为它们发 `MessagesChanged` 和 `PendingOpsChanged`。回放同理：
哪些文件夹的邮件行变了由 repository 返回，core 不猜；只是 op 被删除时不发 `MessagesChanged`，
每次回放结束时发一次 `PendingOpsChanged`。

`Touched` 还带着哪些账户有 op **变成**了失败或冲突：只有 store 的 `PendingOps::failed`（服务器拒绝）
和 `conflict`（新代际、`\Noselect`、移动后的位置不明）把 op 标成非 pending，它们把账户记进去。core
据此在上面的事件之后发 `ChangesRefused`，前端只在这时（以及启动、漏收事件后）去取
`dismiss_settled`，不必每次 `PendingOpsChanged` 都查一次队列。

## 草稿的远端副本

同样绑定 UIDVALIDITY：`drafts.remote_*`（文件夹、UIDVALIDITY、UID、Message-ID、版本）同时设置、同时
清空，删除文件夹或 UIDVALIDITY 变化时由 repository 一起清空。表上的 CHECK 约束让单纯的
`ON DELETE SET NULL` 失败，而不是留下一个悬空的 UID。

不再需要的副本经这个队列删除（`PendingOps::delete_on_server`，按服务器上的位置入队一条永久删除；
同步过的邮件行一并删除）。用户已经移走或删除了那封邮件时不再入队：一封邮件最多一条移动或删除。
只按服务器**刚刚报告的** UIDVALIDITY 下的 UID 入队（APPENDUID，或结算时的 EXAMINE）：本地记下的
代际可能已经过时，还没有同步发现，按它入队的删除之后只会变成冲突、副本留在服务器上。所以其余情况
（删除或发出的草稿、另一代际或另一文件夹里被替换的副本）都先按 Message-ID 找到它，见
[草稿与发信](sending.md#同步到服务器)。
